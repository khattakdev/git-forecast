# git-forecast build guide

From an empty repo to v0.1.0 on npm, launching on January 15, 2027. Each step ends with a check.

## Done

- **Before you start:** npm names checked, `@git-forecast` scope reserved, tools installed.
- **Step 1, repo:** github.com/khattakdev/git-forecast (MIT).
- **Step 2, workspace:** npm workspaces (`packages/core`, `packages/cli`), TypeScript strict built with plain `tsc`, Vitest, Biome. `git forecast -v` works via `npm link -w git-forecast`.
- **Step 3, CI:** lint, build, typecheck, test and a CLI smoke test on Linux, macOS and Windows with Node 22 and 24. `.gitattributes` forces LF.
- **Step 4:** `CLAUDE.md` and these docs.
- **Step 5, test repos:** seven fixture scenarios judged by real Git (`npm run fixtures`, checked in CI) and a speed test (`npm run speed`). Details below.

## Step 5: Test repos first

Build the test repos before the engine, so every feature has a known right answer.

1. Write `fixtures/build.ts`: creates small throwaway repos in a temp folder with plain Git commands, each with a local bare repo acting as `origin`.
2. Scenarios:

| Scenario               | What it tests                                                   |
| ---------------------- | --------------------------------------------------------------- |
| `clean`                | main moved, no files overlap                                    |
| `conflict-step-2`      | rebase stops at your second commit; merge conflicts too         |
| `rebase-only-conflict` | merge would be clean, but an intermediate rebase step conflicts |
| `pushed-branch`        | your branch is on origin, so rebase means a force push          |
| `squash-prs`           | main has squash-merged PRs with `(#123)` in their subjects      |
| `rename`               | main renames a file you edited                                  |
| `messy-local`          | uncommitted changes, unpushed commits, old stashes              |

3. **Real Git is the judge.** For each scenario, run the real `git rebase` and `git merge` in a copy and record the outcome in `fixtures/expected/<name>.json`.
4. **Speed test:** clone a large public repo with `--filter=blob:none`, make a branch that diverges from main, time each command.

Check: `npm run fixtures` builds every scenario, each with an expected file read once by hand.

Status (Nov 15): all seven scenarios built, expected files generated by real Git, `npm run fixtures -- --check` in CI. `npm run speed` on React (21,791 commits): the plain `git forecast` commands sum to ~100 ms; the rebase simulation costs ~13 ms per step (mostly two process starts), so `sync` on a 20-commit branch sums to ~370 ms, over budget. Design for that in the `rebase.ts` note. Expected files read by hand: done.

## Step 6: The core engine

Build in this order; each module passes its fixtures before the next starts.

| Module         | Answers                                                  | Git commands                                                                                                                                                                              |
| -------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `git.ts`       | Run Git safely and fast                                  | `execFile("git", args)` with `GIT_OPTIONAL_LOCKS=0` and `LC_ALL=C`                                                                                                                        |
| `repo.ts`      | Branch, upstream, base branch                            | `git symbolic-ref --quiet --short HEAD`, `git for-each-ref` (`%(upstream)`, `%(upstream:track)` for `[gone]`; `refs/remotes/*/HEAD`, `*/main`, `*/master` for the base)                   |
| `status.ts`    | Ahead/behind, dirty files, unpushed, stashes             | `git status --porcelain=v2 -z --branch -uall`, `git rev-list --left-right --count origin/main...HEAD`, `git stash list --format=%ct%x09%gs`                                               |
| `incoming.ts`  | What moved on main, files, PRs                           | `git log HEAD..origin/main --reverse --first-parent -m -M --name-status -z`; PR numbers from a trailing `(#123)` or `Merge pull request #123`                                             |
| `merge.ts`     | Would a merge conflict, where; refused by local changes? | `git merge-tree --write-tree -z --name-only HEAD origin/main` (exit code 1 = conflicts), `git diff-tree` (files it changes), `git check-attr --stdin` (merge drivers, LFS), rerere config |
| `rebase.ts`    | Which rebase step conflicts                              | One long-running `git merge-tree --stdin`, fed one line per commit: `<commit>^ -- <previous result tree> <commit>`; no `commit-tree` (see Plan from Nov 17, D1–D2)                        |
| `push.ts`      | Force push needed?                                       | Does the rebase rewrite commits already on `@{u}`?                                                                                                                                        |
| `recommend.ts` | Rebase or merge                                          | `.gitforecast.json` rule first; else `git rev-list --merges --first-parent --since=90.days origin/main --count`                                                                           |
| `freshness.ts` | How stale the view is                                    | mtime of `.git/FETCH_HEAD`; suggest `--fetch`                                                                                                                                             |

- Define the output types first in `core/src/types.ts`; the CLI, `--json` and later front ends depend on them.
- Mark uncertainty: custom merge drivers in `.gitattributes`, Git LFS, rerere, and rebase steps after the first conflict.
- Document `git merge-tree --write-tree`: it writes unreferenced trees (no refs, index or files change; Git's cleanup removes them).

Check: every fixture matches its expected file; speed test under 300 ms.

Status (Nov 17): engine complete. `forecastStatus()` / `forecastSync()` match every field of every fixture's expected file; `npm run speed` on React (21,791 commits, 20-commit branch): `git forecast` ~58 ms, `git forecast sync` ~74 ms (median), within 300 ms.

### Plan from Nov 17

The rest of v0 as 8 PRs, built one at a time (tests first, break-checks, CI green, then merge):

1. `merge.ts`: clean / conflict / refused / uncertain, plus what `--autostash` would do.
2. `rebase.ts` with its design note.
3. `push.ts`, `recommend.ts`, `freshness.ts`.
4. `forecast.ts`: `forecastStatus()` and `forecastSync()` assemble the reports; speed test on the real engine.
5. CLI status screen (after `docs/screens.md` is approved).
6. CLI `sync`.
7. README and demo GIF.
8. Release workflow.

Decisions:

| #   | Decision                                                                                                                                                             |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Rebase simulation: one `git merge-tree --stdin` process, fed trees step by step (no `commit-tree`). Measured ~1–6 ms per step vs ~13 ms.                             |
| D2  | Keep Git 2.40+. Probe batch mode once; fall back to one `merge-tree --merge-base` per step if it's missing; below 2.40, "uncertain: git-too-old".                    |
| D3  | Draft both screens in `docs/screens.md` and approve them before CLI code.                                                                                            |
| D4  | Local changes that block a sync: refuse and suggest `git stash` by default. `--autostash` (or `"autostash": true`) opts in; the engine forecasts both (`ifStashed`). |
| D5  | No team rule: merge commits on main's first-parent line in the last 90 days → recommend merge, else rebase ("history-shape").                                        |
| D6  | One PR per item above.                                                                                                                                               |

## Step 7: The CLI

| Command or flag        | Behaviour                                                                                                                   |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `git forecast`         | Smarter status screen (see the v0 mock)                                                                                     |
| `git forecast sync`    | Rebase vs merge, recommendation, then `[r] [m] [d] [q]`                                                                     |
| `--json`               | The core's result as JSON, nothing else                                                                                     |
| `--fetch`              | Runs `git fetch` first; the only network call                                                                               |
| `--base <branch>`      | Compare against another branch                                                                                              |
| `--rebase` / `--merge` | Pick without the prompt                                                                                                     |
| `--autostash`          | Stash tracked changes, sync, re-apply (Git's own `--autostash`); default off, or `"autostash": true` in `.gitforecast.json` |

- Interactive only in a TTY; piped or CI → print and exit.
- Run the chosen command through real Git with live output, then print next steps and how to back out.
- Respect `NO_COLOR` and narrow terminals.
- Exit codes: 0 success, 1 error, 2 "not a Git repo" / "no upstream", each with a one-line fix.

Check: output on `conflict-step-2` matches the v0 mock; same in Windows Terminal.
